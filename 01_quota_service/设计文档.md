# 模拟题 1：资源配额 / 使用限额服务

## 1. 题目

实现一个内部资源配额服务。其他系统可以：

- 为用户/项目设置某类资源的 quota
- 查询当前 usage
- 尝试消费额度
- 如果超过 limit 则拒绝
- 释放已使用额度

例子：

```text
subject = project-123
resource = droplets
limit = 10
used = 7
```

再消费 2：允许；再消费 5：拒绝。

## 2. 三小时 MVP

只做 **quota enforcement**，不要主动升级成完整 rate limiting 平台。

核心 API：

```text
PUT  /quotas/{subject_id}/{resource}
GET  /quotas/{subject_id}/{resource}
POST /quotas/{subject_id}/{resource}/consume
POST /quotas/{subject_id}/{resource}/release
```

## 3. 数据模型

```text
Quota
- subject_id
- resource
- limit_amount
- used
- updated_at
```

复合主键：

```text
(subject_id, resource)
```

因为同一个 subject 对同一种 resource 应只有一条 quota。

## 4. 核心系统设计

```text
Client
  ↓
FastAPI
  ↓
service.py
  ↓
SQLite transaction
  ↓
quota row
```

这里真正值得讲的是：

> consume 不能做成“先读 used → Python 判断 → 再 update”这种松散三步。

因为两个并发请求可能同时读到相同 used。

本 demo 把：

```text
check + increment
```

放进一个 transaction 中。

## 5. 为什么不是完整 Rate Limiter

Quota：

```text
总使用量不能超过 10
```

Rate limit：

```text
一分钟不能超过 10 次
```

如果题目明确要求 rate limit，可以增加：

```text
window_start
request_count
```

或 token bucket：

```text
tokens
last_refill_at
```

但 prompt 只说 quota/usage limit 时，三小时里不要自己加复杂度。

## 6. 关键错误语义

- quota 不存在：404
- consume 超限：429
- 把 limit 改到低于当前 used：409
- amount <= 0：Pydantic validation → 422

## 8. 必测场景

1. 设置 quota
2. 正常 consume
3. consume 到刚好 limit
4. 超限 → 429
5. release
6. quota 不存在 → 404
7. 非法 amount → 422

## 9. Code Review 高频问题

### 为什么 SQLite？
三小时 prototype：零外部依赖、能持久化、能演示 transaction。

### 并发怎么办？
demo 用 SQLite transaction。Production 可以用 PostgreSQL conditional update / row lock，或 Redis atomic script。

### 为什么 429？
因为当前请求由于 usage limit 被拒绝，语义接近 Too Many Requests。也可以讨论具体产品是否更偏 409/403。

### 多 region 怎么做？
这是 consistency trade-off。强一致全局 quota 会增加 latency；也可以把 quota 分配到 region。

## 10. 明确 Out-of-scope

三小时不做：

- Redis cluster
- global multi-region quota
- token bucket
- distributed locks
- audit dashboard
- frontend

4. metrics
