# 模拟题 2：指标采集与阈值告警

## 1. 题目

实现一个小型 metrics service：

- 客户端上报 metric
- 系统存储 metric
- 可以按名称/来源查询最近数据
- 可以创建 threshold rule
- 上报数据满足规则时产生 alert

例子：

```text
cpu_usage = 92
rule: cpu_usage > 80
→ alert
```

## 2. 三小时 MVP

核心对象只有三个：

```text
Metric
AlertRule
Alert
```

核心 API：

```text
POST /metrics
GET  /metrics
POST /rules
GET  /alerts
```

不要做 dashboard，不要做图表，不要做 PromQL。

## 3. Metric 数据模型

```text
event_id
source
metric_name
value
timestamp
```

这里最值得加的是：

```text
event_id UNIQUE
```

因为采集端可能超时后重试。如果没有 idempotency，同一个 metric 可能被存两次、触发两次 alert。

## 4. Rule 数据模型

```text
id
metric_name
operator
threshold
```

MVP 只支持：

```text
gt
gte
lt
lte
```

不做复杂表达式语言。

## 5. Alert 数据模型

```text
id
rule_id
metric_id
triggered_at
message
```

## 6. 数据流

```text
Producer
   ↓ POST /metrics
FastAPI
   ↓
validate / dedupe event_id
   ↓
insert metric
   ↓
load matching rules
   ↓
evaluate rules
   ↓
insert alerts
   ↓
response
```

MVP 同步执行 rule evaluation。

## 7. 为什么三小时里不搭 Kafka

Production 可能是：

```text
agents
→ load balancer
→ queue / Kafka
→ stream processor
→ time-series DB
→ alert engine
```

但三小时主动搭这些，风险极高。

Prototype：

```text
FastAPI + SQLite
```

Production discussion 再讲：

- Kafka
- TSDB
- partitioning
- retention
- downsampling
- asynchronous alert evaluation

## 8. 查询

## 9. Reliability

MVP 真正实现：

- `event_id UNIQUE`
- validation
- alert 持久化

Production 讨论：

- batch ingestion
- backpressure
- retention
- late events
- event time vs ingest time
- alert cooldown
- dedupe/suppression
- notification retry

## 11. 必测场景

1. 上报 metric
2. duplicate event_id → 409
3. 无规则时不产生 alert
4. 超阈值产生 alert
5. 未超阈值不产生 alert
6. query filter 正常

## 12. Code Review 高频问题

### 高吞吐怎么办？
异步 ingestion、message queue、批量写、TSDB。

### 数据无限增长？
retention、partition、downsampling、cold storage。

### 连续 100 次超阈值？
alert grouping / cooldown / suppression。

### timestamp 乱序？
区分 event time 与 ingestion time，并允许 late-event window。

### 为什么同步 alert？
prototype 简单可解释；production 解耦 ingestion 与 alerting。
