# 模拟题 3：任务队列 / 异步执行 / 重试

## 1. 题目

实现一个小型 job service：

- 提交 job
- 后台执行
- 查询状态
- 失败后 retry

状态：

```text
queued
running
succeeded
failed
```

## 2. 三小时 MVP

不要真的搭完整 queue infrastructure。

真实系统可能：

```text
API
→ durable queue
→ worker fleet
→ retry
→ DLQ
```

本 demo：

```text
FastAPI BackgroundTasks + SQLite
```

重点展示：

- persisted job state
- state transition
- attempts
- retry
- max attempts

```text

```

`fail` 是故意保留的，用来稳定演示 failed → retry。

## 5. 状态机

成功：

```text
queued → running → succeeded
```

失败：

```text
queued → running → failed
```

手工 retry：

```text
failed → queued → running
```

## 6. 为什么不自动无限重试

为了：

- deterministic
- 好测试
- 不制造 retry loop

Production：

- exponential backoff
- jitter
- retryable vs non-retryable
- DLQ
- max attempts

## 7. Reliability 核心：重复执行

很多真实队列提供的是：

```text
at-least-once delivery
```

所以 job 可能执行两次。

如果任务是：

```text
charge_card()
```

重复执行很危险。

Production 必须考虑：

- idempotency key
- unique operation ID
- transactional outbox
- dedupe

三小时 demo 不必全实现，但一定要会说。

## 8. Worker crash

如果：

```text
status = running
```

时 worker crash 怎么办？

本 demo 没实现 lease。

Production 可以增加：

```text
running_at
lease_until
```

超时后重新入队。

## 11. Code Review 高频问题

### 为什么 BackgroundTasks 不是 production queue？
它和 API process 生命周期绑定，不 durable，也没有独立 worker。

### Production 换什么？
SQS / RabbitMQ / Redis queue / Kafka，取决于任务语义。

### 怎么防重复执行？
idempotent handler + operation key。

### poison job？
max attempts + DLQ。

### worker crash？
visibility timeout / lease + retry。
